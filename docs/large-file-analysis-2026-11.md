## 1. 先说清楚：哪些「大文件」不该动

`src/pi-ai/providers/*.models.ts` 占了仓库体积的绝大部分，但**全部是自动生成的**：

```
src/pi-ai/providers/openrouter.models.ts          10013 行
src/pi-ai/providers/vercel-ai-gateway.models.ts    3299 行
src/pi-ai/providers/amazon-bedrock.models.ts       1843 行
src/pi-ai/providers/huggingface.models.ts          1482 行
```

文件头明确写着：

```
// This file is auto-generated by scripts/generate-models.ts
// Do not edit manually - run 'npm run generate-models' to update
```

由 `npm run generate-models` 生成、`generate-models:check` 校验漂移。**这些不算技术债**，人工拆分反而会破坏生成流程。

> ⚠️ 但有个副作用：`tsc` 要解析这 ~2.5 万行纯数据，会让类型检查变慢。若要优化，正确做法是**把模型目录改成运行期 JSON 加载**（`resolveJsonModule` 已开启），而不是拆 TS 文件。这是一个独立的性能议题，不属于「代码体量」问题。

## 2. 逐文件分析

### 2.1 `src/server.ts` — 2925 行（最高优先级）

**结构现实**：

```
createAgentServer              2053 行   ← 病灶
safeEvent                       190 行
planSummaryPayload              134 行
parseMessageRequest              77 行
```

**关键发现**：这个文件**已经做过一轮路由拆分**——`src/server/routes/` 下已有 14 个模块（`git.ts` / `permissions.ts` / `plan-act.ts` / `workspace.ts` 等，共 2790 行）。但 `createAgentServer` 仍有 **2053 行、77 个内部闭包**：

```
effectiveRunPolicy, workspace, dataRoot, workspaceRegistry, customModels,
customProviderForModel, resolveSessionModel, sessionPresentation,
defaultWorkspace, workspaceForSession, workspaceIdForSession, sessions,
goalConfig, goalSessions, goalSessionFor, subagentTaskRegistries,
subagentTaskRegistryForSession, pendingServerSubagentWakeups, ... (共 77 个)
```

**这说明**：路由拆分只是把「HTTP 处理函数」搬了出去，而**所有共享状态和闭包仍囤在工厂函数里**。新路由模块通过一个巨大的 context 参数拿依赖，等于把复杂度换了个地方。

**建议拆法**（按依赖顺序，风险从低到高）：

| 步骤 | 目标 | 预期削减 |
|---|---|---|
| 1 | 把 77 个闭包按域分组为 `ServerState` 对象：`sessions` / `goals` / `subagents` / `models` / `workspace` / `runtime` | — |
| 2 | `sessionGate` / `isSessionBusy` / `reserveSession` / `releaseSession` → `server/session-gate.ts` | ~150 行 |
| 3 | `goalSessions` / `goalSessionFor` / goal 相关 → `server/goal-registry.ts` | ~120 行 |
| 4 | `subagentTaskRegistries` / `createSessionSubagentToolSet` → `server/subagent-wiring.ts` | ~200 行 |
| 5 | `resolveSessionModel` / `customModels` / `sessionLlmConfig` → `server/model-resolution.ts` | ~180 行 |
| 6 | 剩余路由注册 → `server/router.ts`，工厂只做组装 | ~600 行 |

预期最终 `server.ts` ≈ 500–700 行。

> ⚠️ 风险提示：`server.ts` 被 **14 个**测试文件直接 import，任何签名变化都会连带改测试。建议**保持 `createAgentServer` 的对外签名不变**，只重构内部。

## 4. ⚠️ 附带发现的真实缺陷

### 4.1 `scripts/check-file-sizes.ts` 无法运行

第 11 行的块注释里写了 `providers/**/*.models.ts`，其中的 `**/` **提前终止了块注释**：

```ts
/**
 * Generated model catalogs (src/pi-ai/providers/**/*.models.ts) are excluded
 * ...
 */
```

`*/` 出现在 `**/` 里，导致注释在第 11 行结束，后面的 `*.models.ts) are excluded` 被当成代码 → `esbuild: Unexpected "*"`。

**影响**：这个守卫脚本**从未成功执行过**。也就是说：
- 1000 行上限**形同虚设**
- `scripts/file-size-baseline.json` **根本不存在**（我确认过文件缺失）

**修复方案**（二选一）：

```ts
// 方案 A：改写注释，避免 */ 序列
 * Generated model catalogs (src/pi-ai/providers/<provider>/*.models.ts) are excluded

// 方案 B：改用行注释
// Generated model catalogs (src/pi-ai/providers/**/*.models.ts) are excluded
```

**修复后还需要**：
1. 在 `package.json` 加 `"check:file-sizes": "tsx scripts/check-file-sizes.ts"`
2. 首次运行 `--update-baseline` 生成 baseline
3. 接入 CI（`.github/workflows/ci.yml`）

> 这条是本次分析**最有价值的发现**：团队以为有体量守卫，实际上没有。

## 5. 我不建议做的事

1. **不要为了行数而拆 `orchestrator.ts`**——21 个方法、最大 100 行，是健康的类。
2. **不要动 `pi-ai/providers/*.models.ts`**——自动生成，改了会被 `generate-models:check` 打回。
3. **不要按「行数达标」做一次性大拆分**——`loop.ts` 和 `server.ts` 的拆分必须分批，每批单独跑测试。
4. **不要在拆 `server.ts` 时改 `createAgentServer` 的对外签名**——**14 个**测试文件依赖它。
